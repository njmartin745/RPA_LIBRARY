# Production Milestone 9 Plan

## 1. Milestone Definition

Production Milestone 9 should refresh the production proof status after Milestones 7 and 8 and plan the first operator-facing proof viewer/demo.

The milestone should remain documentation and demo oriented. It should not expand workflow execution capability. The goal is to make the existing proof foundation easier for a human operator to inspect:

- success proof artifacts from the fixture-bound local-browser path
- controlled runtime failure artifacts from Milestone 8
- action contract status from Milestone 7
- clear disclaimers that the repository is not production-ready yet

## 2. Non-Goals

- Do not add external website support.
- Do not add downloads.
- Do not add credentials.
- Do not add arbitrary workflow execution.
- Do not make `REGISTRY/action_registry.json` authoritative.
- Do not broaden action coverage.
- Do not replace the CLI proof runner.
- Do not create a full application yet.
- Do not claim production readiness.
- Do not change runtime behavior, validation semantics, or existing milestone smokes.

- JSONL logs: `logs/run.jsonl`
- run manifest: `history/run_manifest.json`
- step outcomes: `history/step_outcomes.jsonl`

## 6. Candidate Proof Viewer/Dashboard Scope

The first viewer should be a proof artifact browser, not an execution surface.

It may display:

- latest success proof run
- latest controlled failure proof run
- run status and scenario
- workflow name
- browser used when available
- bundle fingerprint
- step outcomes
- failed step details
- links/paths to generated artifacts
- action contract summary from `docs/analysis/action_contract_alignment_report.md`

It should not run workflows, accept arbitrary workflow paths, or mutate artifacts.

## 7. Minimum Useful Operator-Facing Demo

The smallest useful demo is a generated static HTML page that reads or embeds existing proof artifacts from the latest success and failure run directories.

Minimum demo:

- one page titled `Production Proof Demo`
- two side-by-side run summaries:
  - `Controlled Success: local browser static site`
  - `Controlled Failure: missing selector`
- status badges: pass/error
- run metadata from manifest/report
- step table from `step_outcomes.jsonl`
- failure detail block for the missing selector
- bundle fingerprint block
- artifact path list
- prominent `Not production-ready` notice

This gives an operator something tangible without building a full app.

## 8. What Should Be Visible In The Demo

Visible fields should include:

- scenario name
- run status
- workflow name
- run id
- browser, if recorded by the helper/CLI summary
- bundle version and fingerprint SHA-256
- total steps
- status counts
- step index, action, status, selector_ref/url when safe
- error class/message for failed steps
- report paths
- log path
- manifest path

The demo should redact or avoid displaying secret-bearing fields, matching the existing HISTORY/LOG redaction posture.

## 9. What Should Remain CLI-Only

Keep these CLI/dev-smoke only for Milestone 9:

- running the production proof
- running the controlled failure proof
- browser selection
- headed/headless controls
- output-root controls
- JSON command output
- validation gates
- any arbitrary workflow/deploy bundle path handling

The viewer should consume artifacts after they exist.

## 10. Streamlit Versus Static HTML Versus CLI Report Comparison

Static HTML:

- Pros: no server dependency, easy to open/share, low risk, can be generated from existing artifacts, good fit for a first demo.
- Cons: less interactive; refresh requires regeneration.

Streamlit:

- Pros: quick dashboard, easy filtering and expandable sections.
- Cons: new runtime dependency or environment assumption, needs server process, feels like a larger app surface than the milestone requires.

Generated Markdown/CLI report:

- Pros: already supported by `REPORT-1B`, simple and durable.
- Cons: less operator-friendly for side-by-side success/failure comparison; harder to inspect multiple artifacts at once.

## 11. Recommended First Viewer Approach

Use generated static HTML for Milestone 9.

Recommended shape:

- Add a dev-only script such as `dev/dev_generate_production_proof_demo.py`.
- Add a smoke such as `dev/dev_smoke_production_milestone_9.py`.
- Generate output under ignored unique artifact directories:
  - `dev/_smoke_artifacts/production_milestone_9/run_<time_ns>_<pid>/proof_demo.html`
- Read existing generated proof artifacts from success and failure proof runs.
- If artifacts are absent, the smoke may run existing proof helpers to create controlled local artifacts, but this should be explicit and fixture-bound.

Static HTML keeps the first viewer tangible and avoids overbuilding.

## 12. Required Inputs And Artifact Discovery Strategy

Inputs:

- success proof output directory
- failure proof output directory
- optional output directory for generated demo

Discovery strategy:

- Prefer explicit paths passed by the smoke/helper.
- For developer convenience, optionally discover the newest run directory under known ignored roots:
  - `dev/_smoke_artifacts/production_proof/`
  - `dev/_smoke_artifacts/production_milestone_8/`
- Validate discovered directories by checking required files before rendering.
- Do not search arbitrary user directories.
- Do not accept arbitrary workflow execution inputs.

## 13. Report/History/Log Data To Read

Read:

- `history/run_manifest.json`
- `history/step_outcomes.jsonl`
- `bundle/deploy_bundle_fingerprint.json`
- `report/run_report.json`
- `report/run_report.md`, optionally linked or excerpted
- `logs/run.jsonl`, summarized only

Use structured JSON/JSONL readers where practical. For logs, display:

- count of events
- first/last timestamps if available
- error event count
- path to full log

Do not dump full logs into the first viewer.

## 14. Failure And Success Run Display Requirements

Success display:

- status is pass/ok
- all step outcomes are ok
- bundle fingerprint is present
- artifact list is complete
- browser proof is local/static only

Failure display:

- status is error
- prior `open` step succeeded
- `wait_for_selector` failed against `pm8.missing_element`
- report error step is step 1
- artifact list is complete
- failure is expected and controlled, not a production incident

Side-by-side display should make clear that both are proof fixtures.

## 15. How To Avoid Implying Production Readiness

The viewer and status refresh must state:

- Not production-ready yet.
- Real browser proof is only against controlled local/static pages.
- CLI proof runner is fixture-bound.
- Failure proof covers one controlled missing-selector case.
- Broad retry, external sites, credentials, downloads, arbitrary workflows, and registry authority remain out of scope.

Avoid labels like `production dashboard` or `production monitoring` for the first demo. Use `Production Proof Demo` or `Proof Artifact Viewer`.

## 17. Negative/Regression Test Strategy

Negative tests should prove:

- missing success artifact directory fails clearly
- missing failure artifact directory fails clearly
- malformed report JSON fails clearly
- viewer does not silently report production-ready
- viewer does not execute arbitrary workflow paths
- viewer does not treat absent browser as viewer success if it is responsible for generating proof artifacts

Regression checks:

- Milestones 5-8 smokes continue passing.
- CLI proof runner behavior remains unchanged.
- REPORT/HISTORY modules remain unchanged unless a direct read-only helper is added.

## 19. Risk Assessment

Low to medium risk.

Main risks:

- overbuilding a dashboard instead of a proof viewer
- accidentally implying production readiness
- coupling to transient ignored artifact paths too tightly
- parsing logs/reports ad hoc instead of using structured JSON/JSONL readers
- making the viewer execute arbitrary workflows
- introducing a new dependency such as Streamlit too early

Mitigation:

- static HTML first
- fixture-bound artifact inputs
- explicit disclaimers
- strict artifact validation
- dev-only location
- regression smokes for Milestones 5-8
